# 仓库运行风险评估与修复计划

## 摘要

对仓库（FastAPI 后端 + React/Vite 前端 + Docker Compose 部署）进行了一次聚焦「是否会导致无法正常使用」的风险审计。发现 **1 个高优先级、会直接导致用户频繁掉线的功能缺陷**，以及若干「按默认配置无法启动/开箱即用路径断裂」的中风险项。本计划列出风险清单、每项的依据（文件+逻辑）、建议修复方案与验证步骤。

审计只涉及「会导致无法正常使用」的功能性问题，不含一般性安全加固建议（仓库本身已有较强的 fail-closed 安全设计）。

---

## 现状分析

- 后端基于 FastAPI + SQLAlchemy 2 + Alembic，配置集中在 [config.py](file:///workspace/backend/app/config.py)，生产强制校验在 [config_validation.py](file:///workspace/backend/app/config_validation.py)（`assert_production_config` 在 [main.py](file:///workspace/backend/app/main.py#L61-L65) lifespan 调用）。
- 认证采用「短期 Access Token（默认 900s）+ 可轮换 Refresh Token（HttpOnly Cookie，默认 14 天）」双 token 模型，详见 [routers/auth.py](file:///workspace/backend/app/routers/auth.py)。
- 前端 axios 客户端在 [client.ts](file:///workspace/src/api/client.ts)，认证 API 在 [authApi.ts](file:///workspace/src/api/authApi.ts)，运行模式判定在 [config.ts](file:///workspace/src/config.ts)。
- 部署：docker-compose.yml 定义 postgres/redis/minio/clamav/celery/outbox/backend/frontend 全套服务，后端 healthcheck 走 `/api/ready`。

## 风险清单

### P0 —— 高：会导致用户无法正常使用

#### R1. 前端未实现 Access Token 自动刷新 → 每 15 分钟强制登出（最严重）

- **现象**：用户登录后，后端 Access Token 默认 900 秒（15 分钟）过期；过期后任意接口返回 401，前端 [client.ts](file:///workspace/src/api/client.ts#L123-L145) 的响应拦截器直接调用 `handleUnauthorized()` → 清会话并 `window.location.href = '/login'`，把用户踢回登录页。
- **根因**：
  - 后端已提供 `/api/auth/refresh`（[routers/auth.py](file:///workspace/backend/app/routers/auth.py#L197-L248)），且 Refresh Token 通过 HttpOnly Cookie + SameSite=Lax 下发。
  - 但前端 [authApi.ts](file:///workspace/src/api/authApi.ts) 只有 `login/logout/me`，**没有任何调用 `/auth/refresh` 的代码**；[demoAdapter.ts](file:///workspace/src/services/auth/demoAdapter.ts) 中 `refreshToken` 是 `Promise.reject('Not implemented')`，且从未被调用。
  - 因此 Refresh Token 机制形同虚设，前端每次都要靠用户手动重新登录。
- **触发条件**：任何真实后端登录会话持续超过 15 分钟（开发、生产都触发）。
- **严重程度**：高。这是最直接的「系统无法正常使用」缺陷。

---

### P1 —— 中：按默认配置无法启动 / 开箱即用路径断裂

#### R2. `docker compose up` 按默认值直接启动会因生产守卫拒绝后端启动

- **现象**：docker-compose.yml 的默认值（`SECRET_KEY=change-me-in-production`（22 字符 < 32）、`CORS_ORIGINS` 仅 localhost、`DEMO_USER_PASSWORD=123456`、`NOTIFY_CHANNEL=log`）全部不满足 `assert_production_config()` 的硬性要求，后端容器启动即抛 `RuntimeError` 退出。
- **根因**：[config_validation.py](file:///workspace/backend/app/config_validation.py#L154-L203) 的 fail-closed 校验是**有意的安全设计**，但 README「方式一：Docker Compose 一键部署」[README.md](file:///workspace/README.md#L54-L60) 宣称 `docker compose up -d --build` 即可用，两者冲突——新用户按 README 操作会直接失败，且报错信息不直观。
- **触发条件**：无 `.env` 注入强密钥/白名单时按 README 执行 docker compose 部署。
- **严重程度**：中（设计正确但文档与默认值导致「开箱即用」失败）。

#### R3. 前端 dev 默认既非 mock 也非演示模式 → 后端未启动时前端不可用

- **现象**：README 声称「默认使用 MSW 本地 mock 数据」（[README.md](file:///workspace/README.md#L81)），但实际 `npm run dev` 未设置 `VITE_ENABLE_MSW` 时 MSW 关闭（[main.tsx](file:///workspace/src/main.tsx#L38-L47)），`IS_DEMO_MODE=false` → `IS_PRODUCTION=true`（[config.ts](file:///workspace/src/config.ts#L9-L13)）。
- **后果**：生产模式下前端禁止 mock 回退、禁止快捷登录；若后端未启动，登录页会报「网络错误/离线」，用户无法进入系统。README 描述与实际行为不一致，误导快速上手。
- **触发条件**：仅 `npm install && npm run dev`（不额外配 `.env`），同时后端未运行。
- **严重程度**：中（文档与默认行为不一致，影响快速上手）。

#### R4. 生产就绪依赖整栈全绿，任一外部服务异常即健康检查失败并重启循环

- **现象**：[main.py](file:///workspace/backend/app/main.py#L410-L503) 的 `/api/ready` 要求 PostgreSQL + Redis + S3/MinIO + ClamAV + Celery Worker 全部就绪才返回 200；docker-compose 后端 healthcheck 用它判定健康，失败即 `restart: unless-stopped` 重启。
- **后果**：ClamAV 冷启动需下载病毒库（compose 里 `start_period: 1200s`，官方镜像首次约 20 分钟），期间后端会被判定不健康并反复重启；任一外部服务（S3/Redis/Worker）配置或启动异常，整个系统都无法对外正常服务。
- **严重程度**：中（部署复杂、容错低，容易让「系统不可用」）。

#### R5. 后端 `storage.py` / `scanner.py` 模块级单例在 import 时即执行

- **现象**：`get_storage()` 在 [storage.py](file:///workspace/backend/app/storage.py#L357-L368) 模块末尾以 `storage = get_storage()` 全局单例化；`S3_REQUIRED=true` 且 S3 配置缺失时 import 即抛错。同理 [scanner.py](file:///workspace/backend/app/scanner.py#L333-L356) 的 `get_scanner()` 在 import 阶段可能抛错。
- **后果**：这类「import 期即失败」会让任何尝试导入这些模块的进程（含 worker、脚本、测试 conftest）启动即崩，出错信息与「启动失败」耦合，排查困难。
- **严重程度**：中（影响可维护性与错误可诊断性，间接导致「无法正常使用」）。

## 建议修复方案

> 以下为待用户确认后执行的修复项，按优先级排序。均可独立提交。

### F1（修 R1，最高优先）：前端接入 Refresh Token 自动续期

- 在 [client.ts](file:///workspace/src/api/client.ts) 的响应 401 处理中，先尝试调用 `POST /api/auth/refresh`（携带 HttpOnly Cookie，axios 需 `withCredentials: true`）续取新 Access Token；成功则更新 `localStorage['procurement_token']` 并重放原请求；失败才走 `handleUnauthorized()` 跳登录。
- 需在 [authApi.ts](file:///workspace/src/api/authApi.ts) 新增 `refresh()` 方法；为防并发 401 风暴，加入单飞（single-flight）锁，多个并发 401 只触发一次刷新，其余等待重放。
- 注意：`/auth/refresh` 走 Cookie 认证，`client` 实例需对 refresh 请求启用 `withCredentials`；同时确认 nginx 反代未剥离 `Set-Cookie`。
- 依赖说明：后端 [auth.py](file:///workspace/backend/app/auth.py#L197-L248) REFRESH_COOKIE 已实现，无需改后端。

### F2（修 R2）：docker-compose 提供「能一键启动」的默认值或更清晰失败提示

- 方案 A（推荐）：将 `docker-compose.yml` 默认 `SECRET_KEY` 改为 ≥32 字符的随机默认值、`CORS_ORIGINS` 增加非 localhost 白名单、`NOTIFY_CHANNEL` 说明；或在 README「方式一」前明确要求先 `cp backend/.env.example .env` 并填入强密钥，杜绝「零配置一键部署」的误导。
- 方案 B：新增 `docker-compose.dev.yml`（dev 形态，`APP_ENV=dev`、`SCANNER_PROVIDER=noop`、不强制 S3/Redis），与生产 compose 分离，让快速体验走 dev 形态。

### F3（修 R3）：前端 dev 默认行为对齐文档

- 二选一：
  - 让 `npm run dev` 默认走演示模式（新增 `.env.development` 设置 `VITE_DEMO_MODE=true`），使前端在无后端时仍可快捷登录体验；
  - 或修正 README，明确「默认 MSW 关闭、需真实后端；开启演示需 `VITE_DEMO_MODE=true`」。
- 推荐前者（体验优先），并同步更新 README 默认值表格（R6）。

### F4（修 R5）：避免模块级 import 期抛错

- 将 `storage` / `scanner` 的全局单例延迟到首次使用时初始化（lazy init），或对 import 期抛错做更明确的错误信息，区分「配置缺失」与「真实启动失败」，提升可诊断性。

### F5（低优，可选）：文档对齐

- 修正 README 中 `VITE_ENABLE_MSW` 默认值标注（R6）；评估解耦 `IS_DEMO_MODE` 与 MSW（R8）。

## 复评（F1–F3 落地后）：1 个新的高优先级缺陷 + 2 类常驻用例脆弱性

> 本节由 F1（前端 Access Token 自动续期）落地后的链路复评新增，记录依据与已落地的修复。

### R9 —— 高：同源校验按字符串白名单比对，反代部署下自动续期被 403 挡死

- **现象**：`docker compose` 形态下前端页面在 `http://localhost`（80）打开，Access Token 过期后
  前端按 F1 的实现在 401 时调用 `POST /api/auth/refresh`，后端返回 **403**（跨站请求被拒绝），
  续期失败 → 前端回退到完整登出，用户仍被踢回登录页；F1 的修复在真实部署形态下不生效。
- **根因**：`backend/app/routers/auth.py::_assert_same_origin` 用 `origin not in set(CORS_ORIGINS)`
  逐字符串比对。浏览器序列化 Origin 时会**省略 scheme 默认端口**（MDN「Origin」：
  `http://example.com` 而非 `http://example.com:80`），而仓库内所有默认白名单
  （`docker-compose.yml`、`docker-compose.dev.yml`、`.env.example`）写的都是带 `:80` 的形式，
  两者永不相等。nginx 以 `proxy_set_header Host $host` 反代 `/api`，属同源部署，本不需要 CORS 参与。
- **实测依据**（本机 `docker compose -f docker-compose.dev.yml` 栈，`Host: localhost`）：
  - `Origin: http://localhost` → **403**（浏览器真实会发的值）
  - `Origin: http://localhost:80` → 200（浏览器实际不会发的值）
  - `Origin: http://evil.example.com` → 403（跨站拒绝本身是对的）
- **修复（已落地）**：新增 `_canonical_origin()` 做 origin 归一化（小写、省略 http/https 默认端口），
  放行条件改为「与本次请求自身 origin 同源」∪「归一化后命中 CORS 白名单」，
  与 OWASP CSRF 建议（校验 Origin 是否等于目标 origin，作为纵深防御之一）一致；
  Referer 回退分支复用同一归一化。
- **常驻用例**：`backend/tests/test_security_hardening.py::test_refresh_same_origin_behind_reverse_proxy`
  （含"同源但不在白名单里的域名必须靠同源规则放行""跨站 Origin 仍 403"两侧对照）。
- **浏览器侧端到端**：`e2e/auth-session-refresh.spec.ts` 用真实浏览器断言
  续期请求确实发出且返回 200、原请求自动重放、未被踢回登录页；
  并配反向对照：清掉 refresh cookie 后必须登出，防止"没续期也绿"的假阳性。

### R10 —— 中：F1 的验收方式（人工等 15 分钟）没有沉淀为常驻用例

- 原计划「验证步骤 1」依赖人工调 `ACCESS_TOKEN_TTL` 或等待自然过期，CI 无法回归；
  且原 401 用例的夹具抛的是普通 `Error`（没有 `error.config`），响应拦截器读不到 config，
  **续期分支在用例里根本不可达**，所以"401 会登出"的既有用例对 F1 完全不设防。
- 已补 `src/api/__tests__/client.refresh.test.ts`：夹具改用与 axios `settle()` 完全一致的
  `AxiosError(config/request/response)`，覆盖续期成功、并发单飞、refresh 自身失败登出、
  `_retry` 守卫四条判据（每条都有独立对照）。缺失 `_retry` 守卫时该用例形成
  不让出事件循环的无限微任务链（实测 94% CPU、连测试超时都不触发），故夹具自带调用次数封顶。

### R11 —— 中：依赖"未来日期"的测试夹具会随日历漂移（已修，需长期警惕）

- `src/pages/supplier-portal/__tests__/index.test.tsx` 的夹具写死 `deadline: 2026-08-11`，
  真实时间越过该日后页面进入"已截止"分支、提交按钮 `disabled`，
  3 个提交类用例转为**确定性失败**（`npx vitest run` 常驻门禁自 2026-08-11 起即为红）。
- 同一类问题里更危险的是**不报错的那一类**：`src/__tests__/axe.test.tsx` 的供应商门户
  无障碍扫描用的也是过去的 deadline，它仍然全绿，但扫的已是"已截止"页面变体，
  不再覆盖报价表单；`src/pages/dashboard/__tests__/index.test.tsx` 的 `2026-12-31`
  会在 2027-01-01 之后同样静默漂移。
- 已修：新增 `src/test/temporalFixtures.ts`（`inDays/agoDays`），把被产品代码消费的
  截止/有效期一律改为相对当前时刻生成，并补一条「deadline 已过 → 提交按钮禁用并提示已截止」
  的对照用例，把这条分支显式钉住（原先它只是被夹具无意踩到）。

## 三度复评（把「能数字化的环节全部在线跑通」当验收方式后新增）

> 本节缺陷全部来自实测：`docker compose -f docker-compose.dev.yml` 真实栈（nginx + 单进程
> uvicorn + 容器内 SQLite）+ 真实浏览器 + 真实 HTTP 往返，不是读码推断。
> 每条附"删掉修复会不会红"的反证读数。

### R12 —— 高：SSE 事件流在浏览器侧恒为 401，「免刷新」整条链路是死的

- **现象**：dev 栈每次页面加载都在网络层留下 `401 GET /api/events/stream`；同一 URL 用
  `curl -H "Authorization: Bearer …"` 返回 **200** 并立刻收到 `event: connected`。
  即服务端可用、前端订阅永不生效。
- **根因**：`src/hooks/useEventStream.ts` 用浏览器原生 `EventSource` 建流，而规范不允许
  `EventSource` 携带自定义请求头；后端 `/api/events/stream` 依赖 `get_current_user`（Bearer）。
  token 存在 `localStorage`，两者接不上，属于"实现方式与鉴权方式互斥"的设计缺陷。
- **技术选型（真实检索 npm registry 与包仓库）**：
  - `@microsoft/fetch-event-source`：MIT；功能匹配（fetch 版 SSE，支持自定义头），
    但最新版本 2.0.1 发布于 **2021-04-25**，维护活跃度=停更，风险=依赖层固化了 fetch 语义、
    与本项目已有的退避/补拉逻辑重叠，适配成本中等。
  - `eventsource-parser`：MIT；4.1.1 发布于 **2026-09-15**，活跃；定位是
    "source-agnostic 的 SSE 解析器"，只管解析不管传输，因此鉴权头、`AbortController`、
    退避重连全部由我们自己保留（`createParser({onEvent}).feed()`，重连时 `reset()`）。
  - **选定 `eventsource-parser` + 原生 `fetch`**：功能匹配度等价、License 同为 MIT、
    维护活跃、供应链面最小（不引入第二层 fetch 包装）、不改后端、不改既有重连语义、适配成本最低。
- **修复（已落地）**：`fetch(BASE + '/events/stream', {headers:{Accept:'text/event-stream',
  Authorization}, credentials:'same-origin', signal})` → `ReadableStream` reader →
  `TextDecoder(stream:true)` → `createParser`；保留 2s→30s 指数退避与重连后补拉；
  **每次连接现取 token**（R9 的续期换出的新 token 立即生效）；卸载时 `AbortController.abort()`。
  另把开关接到认证态：`App` 以 `isAuthenticated` 作为 `enabled`，登录前不再发注定 401 的请求，
  "未认证 → 已认证"那一刻立即重连而不是等退避计时。
- **常驻用例 + 反证**：`src/hooks/__tests__/useEventStream.test.ts`（夹具由 `EventSource` 桩
  换成 `fetch` + `ReadableStream` 桩，13 条）。抽掉 `Authorization` 注入 → 2 条红；
  抽掉"连接成功后退避复位"→ 1 条红。浏览器侧 `e2e/sse-live-events.spec.ts` 第 1 条
  断言登录后返回 200、URL 不含 `token=`、且不出现非 200 的建流请求。

### R22 —— 高：SSE 长连接占住请求级 DB session，18 个订阅者即可让整站 API 不可用

  生产 PostgreSQL 形态是 `pool_size=10 + max_overflow=20`，即 30 个浏览器标签页就能打满。
- **修复（已落地）**：端点在交回 `StreamingResponse` 之前显式 `db.close()`
  （鉴权已在依赖阶段完成，后续只从内存队列取事件）。
- **常驻用例 + 反证**：`backend/tests/test_sse_stream_no_db_leak.py`
  直接驱动端点函数：先让一条 session 真正占住连接（`checkedout == before + 1`，前提断言），

### R26 —— 中：E2E 的并发度与四类"看起来像产品问题"的时序假阳性

同机同码、同一 60s 挂钟预算，跑满 5 个项目 180 用例，逐臂读数：

| 配置 / 时机 | 结果 |
| --- | --- |
| `workers=2` | 9 个用例重试后仍红（18.7 分钟），红点集中在 mobile-ios(5) / webkit(2) |
| `workers=1`（首版） | 0 红，但首跑抖动 6~8 个（20.3~21.2 分钟） |
| `workers=1` + 下列 4 项时序修正 | **178 passed / 2 skipped / 0 failed / 0 flaky（7.9 分钟）** |

1. **并发度**：后端是单进程 uvicorn + SQLite，两个 worker 并发把冷启动页面挤出期望预算，
   而省下的时间只有 2.5 分钟 —— 配置固定 `workers: 1`。
2. **登录预算**：登录是全套件最重的一次请求（服务端要跑 bcrypt）。`helpers.login()` 原先只靠
   `expect(page).toHaveURL(...)` 的 10s 预算，实测一次全量跑里 3 次停在 `/login`
   （24 次轮询全是 `/login`）。改为先 `waitForResponse` 断言登录接口返回 2xx，再给跳转 30s。
   顺带删掉 `exception-scenarios.spec.ts` 里重复实现的那份 login（同一缺陷不该修两遍）。
3. **收起的弹层 DOM 仍挂在页面里**：antd Dropdown 关闭后节点只是 `hidden`，
   `.ant-dropdown-menu-item` 会命中上一次展开留下的隐藏节点（实测 firefox 报 `Received: hidden`）；
   选择器一律加 `:not(.ant-dropdown-hidden)` 作用域。
4. **瞬时 toast 断言既歧义又脆弱**：只断 `.ant-message-success` 存在时，前一步遗留的成功提示
   同样能满足（假绿），而 webkit 上等不到当步提示时又会 5s 超时（假红）。core-flow 的 7 处
   改为继承配置预算；`请求超时` 那条按 R25 换成"错误 toast + 乐观更新回滚"双断言。
5. 另有一处与窄屏无关的真实遮挡：报价对比页卡片被**已展开的侧栏子菜单浮层**
   （`ul.ant-menu-sub#...-quotation-group-popup`）压住而点不到。该卡片本身已提供
   `role="button"` + Enter 处理（并有常驻单测钉住），用例改走键盘等价触发。

残留（已量化、未修）：侧栏子菜单浮层会盖住内容区元素。桌面鼠标操作下真实用户是否会被挡住，
本轮没有单独取证（只在长页面 + 命中测试场景里暴露），登记为后续可用性核查项。
