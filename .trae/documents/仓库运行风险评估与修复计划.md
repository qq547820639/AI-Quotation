# 仓库运行风险评估与修复计划

## 摘要

对仓库（FastAPI 后端 + React/Vite 前端 + Docker Compose 部署）进行了一次聚焦「是否会导致无法正常使用」的风险审计。发现 **1 个高优先级、会直接导致用户频繁掉线的功能缺陷**，以及若干「按默认配置无法启动/开箱即用路径断裂」的中风险项。本计划列出风险清单、每项的依据（文件+逻辑）、建议修复方案与验证步骤。

审计只涉及「会导致无法正常使用」的功能性问题，不含一般性安全加固建议（仓库本身已有较强的 fail-closed 安全设计）。

---

## 现状分析

- 后端基于 FastAPI + SQLAlchemy 2 + Alembic，配置集中在 [config.py](file:///workspace/backend/app/config.py)，生产强制校验在 [config_validation.py](file:///workspace/backend/app/config_validation.py)（`assert_production_config` 在 [main.py](file:///workspace/backend/app/main.py#L61-L65) lifespan 调用）。
- 认证采用「短期 Access Token（默认 900s）+ 可轮换 Refresh Token（HttpOnly Cookie，默认 14 天）」双 token 模型，详见 [routers/auth.py](file:///workspace/backend/app/routers/auth.py)。
- 前端 axios 客户端在 [client.ts](file:///workspace/src/api/client.ts)，认证 API 在 [authApi.ts](file:///workspace/src/api/authApi.ts)，运行模式判定在 [config.ts](file:///workspace/src/config.ts)。
- 部署：docker-compose.yml 定义 postgres/redis/minio/clamav/celery/outbox/backend/frontend 全套服务，后端 healthcheck 走 `/api/ready`。

## 风险清单

### P0 —— 高：会导致用户无法正常使用

#### R1. 前端未实现 Access Token 自动刷新 → 每 15 分钟强制登出（最严重）

- **现象**：用户登录后，后端 Access Token 默认 900 秒（15 分钟）过期；过期后任意接口返回 401，前端 [client.ts](file:///workspace/src/api/client.ts#L123-L145) 的响应拦截器直接调用 `handleUnauthorized()` → 清会话并 `window.location.href = '/login'`，把用户踢回登录页。
- **根因**：
  - 后端已提供 `/api/auth/refresh`（[routers/auth.py](file:///workspace/backend/app/routers/auth.py#L197-L248)），且 Refresh Token 通过 HttpOnly Cookie + SameSite=Lax 下发。
  - 但前端 [authApi.ts](file:///workspace/src/api/authApi.ts) 只有 `login/logout/me`，**没有任何调用 `/auth/refresh` 的代码**；[demoAdapter.ts](file:///workspace/src/services/auth/demoAdapter.ts) 中 `refreshToken` 是 `Promise.reject('Not implemented')`，且从未被调用。
  - 因此 Refresh Token 机制形同虚设，前端每次都要靠用户手动重新登录。
- **触发条件**：任何真实后端登录会话持续超过 15 分钟（开发、生产都触发）。
- **严重程度**：高。这是最直接的「系统无法正常使用」缺陷。

---

### P1 —— 中：按默认配置无法启动 / 开箱即用路径断裂

#### R2. `docker compose up` 按默认值直接启动会因生产守卫拒绝后端启动

- **现象**：docker-compose.yml 的默认值（`SECRET_KEY=change-me-in-production`（22 字符 < 32）、`CORS_ORIGINS` 仅 localhost、`DEMO_USER_PASSWORD=123456`、`NOTIFY_CHANNEL=log`）全部不满足 `assert_production_config()` 的硬性要求，后端容器启动即抛 `RuntimeError` 退出。
- **根因**：[config_validation.py](file:///workspace/backend/app/config_validation.py#L154-L203) 的 fail-closed 校验是**有意的安全设计**，但 README「方式一：Docker Compose 一键部署」[README.md](file:///workspace/README.md#L54-L60) 宣称 `docker compose up -d --build` 即可用，两者冲突——新用户按 README 操作会直接失败，且报错信息不直观。
- **触发条件**：无 `.env` 注入强密钥/白名单时按 README 执行 docker compose 部署。
- **严重程度**：中（设计正确但文档与默认值导致「开箱即用」失败）。

#### R3. 前端 dev 默认既非 mock 也非演示模式 → 后端未启动时前端不可用

- **现象**：README 声称「默认使用 MSW 本地 mock 数据」（[README.md](file:///workspace/README.md#L81)），但实际 `npm run dev` 未设置 `VITE_ENABLE_MSW` 时 MSW 关闭（[main.tsx](file:///workspace/src/main.tsx#L38-L47)），`IS_DEMO_MODE=false` → `IS_PRODUCTION=true`（[config.ts](file:///workspace/src/config.ts#L9-L13)）。
- **后果**：生产模式下前端禁止 mock 回退、禁止快捷登录；若后端未启动，登录页会报「网络错误/离线」，用户无法进入系统。README 描述与实际行为不一致，误导快速上手。
- **触发条件**：仅 `npm install && npm run dev`（不额外配 `.env`），同时后端未运行。
- **严重程度**：中（文档与默认行为不一致，影响快速上手）。

#### R4. 生产就绪依赖整栈全绿，任一外部服务异常即健康检查失败并重启循环

- **现象**：[main.py](file:///workspace/backend/app/main.py#L410-L503) 的 `/api/ready` 要求 PostgreSQL + Redis + S3/MinIO + ClamAV + Celery Worker 全部就绪才返回 200；docker-compose 后端 healthcheck 用它判定健康，失败即 `restart: unless-stopped` 重启。
- **后果**：ClamAV 冷启动需下载病毒库（compose 里 `start_period: 1200s`，官方镜像首次约 20 分钟），期间后端会被判定不健康并反复重启；任一外部服务（S3/Redis/Worker）配置或启动异常，整个系统都无法对外正常服务。
- **严重程度**：中（部署复杂、容错低，容易让「系统不可用」）。

#### R5. 后端 `storage.py` / `scanner.py` 模块级单例在 import 时即执行

- **现象**：`get_storage()` 在 [storage.py](file:///workspace/backend/app/storage.py#L357-L368) 模块末尾以 `storage = get_storage()` 全局单例化；`S3_REQUIRED=true` 且 S3 配置缺失时 import 即抛错。同理 [scanner.py](file:///workspace/backend/app/scanner.py#L333-L356) 的 `get_scanner()` 在 import 阶段可能抛错。
- **后果**：这类「import 期即失败」会让任何尝试导入这些模块的进程（含 worker、脚本、测试 conftest）启动即崩，出错信息与「启动失败」耦合，排查困难。
- **严重程度**：中（影响可维护性与错误可诊断性，间接导致「无法正常使用」）。

## 建议修复方案

> 以下为待用户确认后执行的修复项，按优先级排序。均可独立提交。

### F1（修 R1，最高优先）：前端接入 Refresh Token 自动续期

- 在 [client.ts](file:///workspace/src/api/client.ts) 的响应 401 处理中，先尝试调用 `POST /api/auth/refresh`（携带 HttpOnly Cookie，axios 需 `withCredentials: true`）续取新 Access Token；成功则更新 `localStorage['procurement_token']` 并重放原请求；失败才走 `handleUnauthorized()` 跳登录。
- 需在 [authApi.ts](file:///workspace/src/api/authApi.ts) 新增 `refresh()` 方法；为防并发 401 风暴，加入单飞（single-flight）锁，多个并发 401 只触发一次刷新，其余等待重放。
- 注意：`/auth/refresh` 走 Cookie 认证，`client` 实例需对 refresh 请求启用 `withCredentials`；同时确认 nginx 反代未剥离 `Set-Cookie`。
- 依赖说明：后端 [auth.py](file:///workspace/backend/app/auth.py#L197-L248) REFRESH_COOKIE 已实现，无需改后端。

### F2（修 R2）：docker-compose 提供「能一键启动」的默认值或更清晰失败提示

- 方案 A（推荐）：将 `docker-compose.yml` 默认 `SECRET_KEY` 改为 ≥32 字符的随机默认值、`CORS_ORIGINS` 增加非 localhost 白名单、`NOTIFY_CHANNEL` 说明；或在 README「方式一」前明确要求先 `cp backend/.env.example .env` 并填入强密钥，杜绝「零配置一键部署」的误导。
- 方案 B：新增 `docker-compose.dev.yml`（dev 形态，`APP_ENV=dev`、`SCANNER_PROVIDER=noop`、不强制 S3/Redis），与生产 compose 分离，让快速体验走 dev 形态。

### F3（修 R3）：前端 dev 默认行为对齐文档

- 二选一：
  - 让 `npm run dev` 默认走演示模式（新增 `.env.development` 设置 `VITE_DEMO_MODE=true`），使前端在无后端时仍可快捷登录体验；
  - 或修正 README，明确「默认 MSW 关闭、需真实后端；开启演示需 `VITE_DEMO_MODE=true`」。
- 推荐前者（体验优先），并同步更新 README 默认值表格（R6）。

### F4（修 R5）：避免模块级 import 期抛错

- 将 `storage` / `scanner` 的全局单例延迟到首次使用时初始化（lazy init），或对 import 期抛错做更明确的错误信息，区分「配置缺失」与「真实启动失败」，提升可诊断性。

### F5（低优，可选）：文档对齐

- 修正 README 中 `VITE_ENABLE_MSW` 默认值标注（R6）；评估解耦 `IS_DEMO_MODE` 与 MSW（R8）。

## 复评（F1–F3 落地后）：1 个新的高优先级缺陷 + 2 类常驻用例脆弱性

> 本节由 F1（前端 Access Token 自动续期）落地后的链路复评新增，记录依据与已落地的修复。

### R9 —— 高：同源校验按字符串白名单比对，反代部署下自动续期被 403 挡死

- **现象**：`docker compose` 形态下前端页面在 `http://localhost`（80）打开，Access Token 过期后
  前端按 F1 的实现在 401 时调用 `POST /api/auth/refresh`，后端返回 **403**（跨站请求被拒绝），
  续期失败 → 前端回退到完整登出，用户仍被踢回登录页；F1 的修复在真实部署形态下不生效。
- **根因**：`backend/app/routers/auth.py::_assert_same_origin` 用 `origin not in set(CORS_ORIGINS)`
  逐字符串比对。浏览器序列化 Origin 时会**省略 scheme 默认端口**（MDN「Origin」：
  `http://example.com` 而非 `http://example.com:80`），而仓库内所有默认白名单
  （`docker-compose.yml`、`docker-compose.dev.yml`、`.env.example`）写的都是带 `:80` 的形式，
  两者永不相等。nginx 以 `proxy_set_header Host $host` 反代 `/api`，属同源部署，本不需要 CORS 参与。
- **实测依据**（本机 `docker compose -f docker-compose.dev.yml` 栈，`Host: localhost`）：
  - `Origin: http://localhost` → **403**（浏览器真实会发的值）
  - `Origin: http://localhost:80` → 200（浏览器实际不会发的值）
  - `Origin: http://evil.example.com` → 403（跨站拒绝本身是对的）
- **修复（已落地）**：新增 `_canonical_origin()` 做 origin 归一化（小写、省略 http/https 默认端口），
  放行条件改为「与本次请求自身 origin 同源」∪「归一化后命中 CORS 白名单」，
  与 OWASP CSRF 建议（校验 Origin 是否等于目标 origin，作为纵深防御之一）一致；
  Referer 回退分支复用同一归一化。
- **常驻用例**：`backend/tests/test_security_hardening.py::test_refresh_same_origin_behind_reverse_proxy`
  （含"同源但不在白名单里的域名必须靠同源规则放行""跨站 Origin 仍 403"两侧对照）。
- **浏览器侧端到端**：`e2e/auth-session-refresh.spec.ts` 用真实浏览器断言
  续期请求确实发出且返回 200、原请求自动重放、未被踢回登录页；
  并配反向对照：清掉 refresh cookie 后必须登出，防止"没续期也绿"的假阳性。

### R10 —— 中：F1 的验收方式（人工等 15 分钟）没有沉淀为常驻用例

- 原计划「验证步骤 1」依赖人工调 `ACCESS_TOKEN_TTL` 或等待自然过期，CI 无法回归；
  且原 401 用例的夹具抛的是普通 `Error`（没有 `error.config`），响应拦截器读不到 config，
  **续期分支在用例里根本不可达**，所以"401 会登出"的既有用例对 F1 完全不设防。
- 已补 `src/api/__tests__/client.refresh.test.ts`：夹具改用与 axios `settle()` 完全一致的
  `AxiosError(config/request/response)`，覆盖续期成功、并发单飞、refresh 自身失败登出、
  `_retry` 守卫四条判据（每条都有独立对照）。缺失 `_retry` 守卫时该用例形成
  不让出事件循环的无限微任务链（实测 94% CPU、连测试超时都不触发），故夹具自带调用次数封顶。

### R11 —— 中：依赖"未来日期"的测试夹具会随日历漂移（已修，需长期警惕）

- `src/pages/supplier-portal/__tests__/index.test.tsx` 的夹具写死 `deadline: 2026-08-11`，
  真实时间越过该日后页面进入"已截止"分支、提交按钮 `disabled`，
  3 个提交类用例转为**确定性失败**（`npx vitest run` 常驻门禁自 2026-08-11 起即为红）。
- 同一类问题里更危险的是**不报错的那一类**：`src/__tests__/axe.test.tsx` 的供应商门户
  无障碍扫描用的也是过去的 deadline，它仍然全绿，但扫的已是"已截止"页面变体，
  不再覆盖报价表单；`src/pages/dashboard/__tests__/index.test.tsx` 的 `2026-12-31`
  会在 2027-01-01 之后同样静默漂移。
- 已修：新增 `src/test/temporalFixtures.ts`（`inDays/agoDays`），把被产品代码消费的
  截止/有效期一律改为相对当前时刻生成，并补一条「deadline 已过 → 提交按钮禁用并提示已截止」
  的对照用例，把这条分支显式钉住（原先它只是被夹具无意踩到）。

## 三度复评（把「能数字化的环节全部在线跑通」当验收方式后新增）

> 本节缺陷全部来自实测：`docker compose -f docker-compose.dev.yml` 真实栈（nginx + 单进程
> uvicorn + 容器内 SQLite）+ 真实浏览器 + 真实 HTTP 往返，不是读码推断。
> 每条附"删掉修复会不会红"的反证读数。

### R12 —— 高：SSE 事件流在浏览器侧恒为 401，「免刷新」整条链路是死的

- **现象**：dev 栈每次页面加载都在网络层留下 `401 GET /api/events/stream`；同一 URL 用
  `curl -H "Authorization: Bearer …"` 返回 **200** 并立刻收到 `event: connected`。
  即服务端可用、前端订阅永不生效。
- **根因**：`src/hooks/useEventStream.ts` 用浏览器原生 `EventSource` 建流，而规范不允许
  `EventSource` 携带自定义请求头；后端 `/api/events/stream` 依赖 `get_current_user`（Bearer）。
  token 存在 `localStorage`，两者接不上，属于"实现方式与鉴权方式互斥"的设计缺陷。
- **技术选型（真实检索 npm registry 与包仓库）**：
  - `@microsoft/fetch-event-source`：MIT；功能匹配（fetch 版 SSE，支持自定义头），
    但最新版本 2.0.1 发布于 **2021-04-25**，维护活跃度=停更，风险=依赖层固化了 fetch 语义、
    与本项目已有的退避/补拉逻辑重叠，适配成本中等。
  - `eventsource-parser`：MIT；4.1.1 发布于 **2026-09-15**，活跃；定位是
    "source-agnostic 的 SSE 解析器"，只管解析不管传输，因此鉴权头、`AbortController`、
    退避重连全部由我们自己保留（`createParser({onEvent}).feed()`，重连时 `reset()`）。
  - **选定 `eventsource-parser` + 原生 `fetch`**：功能匹配度等价、License 同为 MIT、
    维护活跃、供应链面最小（不引入第二层 fetch 包装）、不改后端、不改既有重连语义、适配成本最低。
- **修复（已落地）**：`fetch(BASE + '/events/stream', {headers:{Accept:'text/event-stream',
  Authorization}, credentials:'same-origin', signal})` → `ReadableStream` reader →
  `TextDecoder(stream:true)` → `createParser`；保留 2s→30s 指数退避与重连后补拉；
  **每次连接现取 token**（R9 的续期换出的新 token 立即生效）；卸载时 `AbortController.abort()`。
  另把开关接到认证态：`App` 以 `isAuthenticated` 作为 `enabled`，登录前不再发注定 401 的请求，
  "未认证 → 已认证"那一刻立即重连而不是等退避计时。
- **常驻用例 + 反证**：`src/hooks/__tests__/useEventStream.test.ts`（夹具由 `EventSource` 桩
  换成 `fetch` + `ReadableStream` 桩，13 条）。抽掉 `Authorization` 注入 → 2 条红；
  抽掉"连接成功后退避复位"→ 1 条红。浏览器侧 `e2e/sse-live-events.spec.ts` 第 1 条
  断言登录后返回 200、URL 不含 `token=`、且不出现非 200 的建流请求。

### R22 —— 高：SSE 长连接占住请求级 DB session，18 个订阅者即可让整站 API 不可用

- **修复（已落地）**：端点在交回 `StreamingResponse` 之前显式 `db.close()`

- **常驻用例 + 反证**：`backend/tests/test_sse_stream_no_db_leak.py`

### R27 —— 高：干净签出复现不出 E2E 的绿（种子密码三处副本漂移，401 被放大成全线 429）

- 触发场景是本轮收尾审计本身：`git worktree add --detach /tmp/qi-audit HEAD`（工作树与提交一致）
  → `docker compose -f docker-compose.dev.yml -p qqi-audit up -d --build`（镜像由该树重建，栈 healthy）
  → `npx playwright test`：**第 1 个用例即红**，与 R26 的"首跑抖动"形状完全不同（1.2~1.8s 稳定复现）。
- 归因链（逐条实测，不含推断）：
  1. 第一个假设是"镜像里 MSW 开着、请求被前端 mock 吃掉"（因为工作树缺未跟踪的 `.env.production`）。
     **被容器日志反驳**：`path: /api/auth/login` 有真实响应，`duration_ms` 288~789（bcrypt 量级），
     且 `Dockerfile.frontend` 是 `RUN VITE_ENABLE_MSW=false VITE_API_BASE_URL=/api npm run build` 内联注入，
     宿主 `.env.production` 根本不参与镜像构建。该假设作废。
  2. 日志真实序列：22:42:03–22:42:11 五个 `status: 401`，之后一律 `429`。
  3. `app/routers/auth.py:207` 的 `is_login_blocked()`：连续失败计数达到 `LOGIN_MAX_ATTEMPTS`（默认 5）
     即直接 429 —— 所以 429 只是**放大器**，把它读成限流缺陷会修错地方。
  4. 401 的根因是同一个事实有三份手写副本：`docker-compose.dev.yml` 给后端注入
     `DEMO_USER_PASSWORD=dev-demo-pass-12345678`（种子用户按它做哈希），而 `e2e/helpers.ts` 的兜底值是
     `123456`（等于后端 `config.py:97` 默认值，但不等于 dev compose 的覆盖值）。
  5. CI 为什么是绿的：`ci.yml` 的 docker-e2e job 在 compose 步骤与 playwright 步骤**各写一次**同一个
     `format('ci-e2e-{0}-strong-password', github.run_id)`，宿主 env 盖住了 helpers 的兜底值。
     即"绿"依赖一个未写进仓库的宿主环境变量 —— 本地 dev 形态没有它，兜底值立刻裸露。
     `CHANGELOG.md:195` 记的 `test123`→`123456` 是同类缺陷第二次发生，本轮是第三次。
- 修法（三件，缺一不可）：
  1. dev compose 改 `- DEMO_USER_PASSWORD=${DEMO_USER_PASSWORD:-dev-demo-pass-12345678}`。
     此前是硬赋值，宿主 env **传不进去**，README"可通过 DEMO_USER_PASSWORD 覆盖"只对改文件的人生效

  2. `e2e/helpers.ts` 兜底值对齐，并把 `login()` 的断言文案按 401 / 429 分开写根因与复算命令。
  3. 新增常驻门禁 `scripts/check-e2e-demo-password.mjs`（`npm run e2e:config:check`）：机械核对
     dev compose 默认值 / helpers 兜底值 / README 承诺值三处副本必须相等，锚点未命中即失败；
     自带 `--self-test` 两条反证（注入漂移必须翻红、删位点必须报"锚点未命中"），
     并接在 CI docker-e2e job 启动 compose **之前**（先判契约再起栈，避免 180 个用例替一次配置漂移买单）。
- 读数：`✔ 演示密码一致性检查通过：3 处位点同为 dev-demo-pass-12345678，宿主 env 可整体覆盖`、
  `✔ 自检通过：真实仓库三处一致（dev-demo-pass-12345678），注入漂移与删除位点均会翻红`；
  重启后端容器清掉进程内失败计数后，同一命令 `env -u DEMO_USER_PASSWORD npx playwright test --project=chromium e2e/auth.spec.ts`
  → `2 passed (29.8s)`（修复前在同一干净宿主环境下是 2 红）。
- 顺带更正 README E2E 段的两处失真：写"7 个文件 / 28 条用例"（实为 10 个 spec 文件 / 36 条 `test()` 声明
  × 5 项目 = 180 用例实例，已按 `ls e2e/*.spec.ts`、`grep -c test(` 现算），且"需先 `docker compose up -d --build`"

### R28 —— 高：向导「创建→立刻发送」之间落一次并发刷新，"发送"就静默不发请求，服务端留下孤儿 DRAFT

- 现场：HEAD `5e6bc22` 全量跑里那 1 个抖动 `core-flow.spec.ts:93`（60s 测试预算耗尽）。
  失败截图停在第 4 步预览（两家供应商已选、发送按钮带焦点环），后端日志有
  `POST /api/inquiries` 200（23:25:34）却**没有随后的 `/send`**（下一条 `/send` 是 23:26:35 的重跑）。
- 机制（读码 + 日志对齐，已证实）：
  - `sendInquiry` 入口有 `if (!get().getInquiryById(id)) return notFound()`；
  - `loadFromApi` 是 `set({ inquiries: data })` **整体替换**；
  - 向导 `onOk` 是 `await addInquiry(draft)` → `await sendInquiry(draft.id)` 两次 await，
    中间只要落一次刷新（SSE 重连补拉、列表页 refetch 都会触发），刚建的单就被
    "不含它的服务端快照"挤出缓存 → 本地 `notFound()` 短路；
  - 而 `onOk` 的 `if (!sent.success) return;` 不弹提示 —— 行内注释写的是"axios 拦截器已弹提示"，
    但本地短路**根本没走网络**，拦截器无从弹起 → 用户点了发送却什么都没发生。
- 修法（三处，配套一条常驻用例）：
  1. `sendInquiry` 去掉"本地缓存里有"这道前置条件，记录存在性交回服务端判定；
  2. `applyServerInquiry` 在缓存缺该实体时**插入**而非只 merge（否则请求成功也补不回视图）；
  3. `create/index.tsx` 的 `onOk` 对 `reason=not_found|pending` 这类未走网络的失败补 `notifyError`
     （网络类失败仍交给拦截器，不重复弹）。
  E2E 侧 `createAndSendInquiry` 改为先挂 `waitForResponse(/\/send$/)` 再点发送并断言 2xx，
  把"60s 后 waitForURL 超时"换成"一步之内指名是没发请求还是发了没跳转"。
- 常驻用例：`src/store/__tests__/useInquiryStore.test.ts` 末尾的「并发刷新与刚创建实体之间的竞态（R28）」，
  先红（断在 `sent.success`）后绿。变异对照两条都开火：只回退 (1) → 断在 `sent.success`；
  只回退 (2) → 断在 `after?.status`（`expected undefined to be 'INQUIRING'`）。
- 残留（同形未修，已定位）：`src/store/useInquiryStore.ts` 还有 8 处同样的 `notFound()` 前置短路 ——
  `updateInquiry:214`、`deleteInquiry:240`、`cancelInquiry:306`、`selectSupplier:418`、
  `confirmInquiry:472`、`submitForApproval:514`、`approveInquiry:569`、`rejectInquiry:622`。

### R31 残留 —— mailpit 的同形健康检查：实测后判**不是缺陷**（残留闭合）

R31 当时因为"本机没有该镜像"未取证，只登记不改。本轮拉了 `axllent/mailpit:latest`
（amd64 镜像经 qemu 模拟跑通，不影响结论）在最简容器里实测成对判据：

| 探法 | rc | 说明 |
| --- | --- | --- |
| `wget --spider -q http://localhost:8025` | **0** | 与 nginx 那例不同，这条是绿的 |
| `wget --spider -q http://127.0.0.1:8025` | **0** | 两族都通 |
| `wget --spider -q "http://[::1]:8025"` | **0** | 直接打 IPv6 也通 |
| `wget --spider -q http://localhost:8026`（无监听） | **1** | 反向对照：判据会开火，不是恒绿 |

`docker inspect` 同时报该容器 **healthy**。根因差别在监听族：mailpit 的日志是
`[http] starting on [::]:8025`，`netstat -ltn` 只有 `:::8025` 一行 —— Go 的
`net.Listen("tcp", ":8025")` 默认双栈，IPv6 socket 同时收 IPv4-mapped 连接；
而 nginx 那例是 `listen 80;` 仅 IPv4，busybox wget 先试 `::1` 且不回退才会永远红。

### R21 残留 —— 门户拿到 409 后到底提示什么：取证后判**有缺陷，已修**

R21 的修复让后端把重复冲突变成结构化 409，但当时留了一句"门户前端拿到 409 后的提示与
改价重提路径未取证"。本轮取证：

- 后端真正发出去的形状是 `{"detail": {"error_type": "duplicate_quotation",
  "message": "该供应商已存在此询价单的报价，请勿重复创建", "inquiryId", "supplierId"}}`
  （取自常驻用例 `backend/tests/test_invitation_security.py:470` 对
  `r.json()["detail"]["error_type"]` 的断言，不是我推测的）。
- 前端 `parseApiError` 的 409 分支只读**顶层** `data.message`，
  而 `extractBackendMessage` 虽被 `default:` 分支调用，却只看 `detail`（字符串）与 `detail.msg`，
  **不看 `detail.message`**。两侧一错开：后端专门写的用户文案在门户被丢掉。
- 实测（`src/api/__tests__/client.test.ts` 新_describe_ 的第一轮红）：
  四种 409 载荷 —— `detail` 对象带 `message`、`detail` 纯字符串、带 `error_type`、
  以及只有 `error_type` —— **全部**塌成同一句通用文案
  `数据已被他人修改或存在冲突，请刷新后重试`。也就是说这不止 R21 那一个口，
  凡走 FastAPI `detail` 信封的 409 都拿不到可执行提示。

1. `extractBackendMessage` 补 `detail.message`；
2. 新增 `detail.error_type → i18n key` 映射（`duplicate_quotation → errors.duplicateQuotation`），

3. 只在 409 分支放开优先级：`i18n(error_type) ?? 顶层 message ?? detail 文案 ?? 通用冲突提示`。
   401/403 **故意不动**：那里固定用前端文案是既有决定，
   常驻用例「403 响应：提示权限不足（国际化文案）」正钉着它（给 403 透出后端文本会被这条判红）。

### 一次被变异对照抓到的假绿（必须留档，因为写它的时候我以为自己有牙齿）

第一版 R32 用例的反向断言是
`expect(page.locator('.ant-message-success').filter({hasText:/已确认定标/})).toHaveCount(0)`。
把实现改回"不 await 就弹成功"、重建前端镜像、重跑 —— **用例仍然通过**，而且 5 个项目全绿时
我差点把它当成 R32 已修的证据。用一次性探针直接 dump DOM 才看清变异档的真实状态：

```
RESP 500
T+0ms    success=2 error=1 :: |已选择推荐供应商|已确认定标|boom|
T+1500ms success=2 error=1 :: （同上）
T+3500ms success=0 error=0 :: (无 .ant-message)
```

根因是断言形状而非时序巧合：**antd message 3 秒自动消失，而 `toHaveCount(0)` 是会重试的负向断言**
—— 它先看到 1，继续轮询，元素淡出后看到 0 就判通过。同一条断言在正确实现和缺陷实现上都给绿，
等于零判别。改法不是调 timeout（只是换个时点赌运气），而是**把取样从"事后看一眼"改成"从头连续记录"**：
点击之前先装 `MutationObserver` 把每条 `类型|文案` 记进 `window.__toasts`，事后对这份记录断言，
并把记录本身印进失败消息。两档对照（同一镜像路径，只换实现）：

| 档 | 实现 | 结果 |
| --- | --- | --- |
| 变异档 | `confirmInquiry(id); notifySuccess(已确认定标)` 不 await | **红**，`Error: 定标失败时不得出现成功提示，实际抓到：["success\|已选择推荐供应商","success\|已确认定标","error\|boom"]`，退出码 1 |

### R35 —— 高：写边界不校验，读边界必炸；且一条坏行毒掉整个列表页

- 三个互相独立的事实（每个都单独量过）：
  1. **写侧原样透传**：`backend/app/routers/inquiries.py:133`（改前）
     `quantity=it.get("quantity", 0)`，而 `InquiryCreate` 是 `extra="allow"` 且只校验
     `subject`（`schemas.py:261-272`）。SQLite 列不做类型校验，
     于是 `quantity="NOT-A-NUMBER"` 能落库（表上的 `CHECK (quantity > 0)` 也拦不住：
     SQLite 里 TEXT 的排序类高于 INTEGER，`'NOT-A-NUMBER' > 0` 为真）。
  2. **读侧要求 int**：`InquiryItemSchema.quantity: int`（`schemas.py:108`）。
     traceback 的叶子帧就是这里：
     `serializers.py:94 inquiry_item_to_schema → pydantic_core.ValidationError:
     quantity Input should be a valid integer ... input_value='NOT-A-NUMBER'`。
  3. **爆炸半径是整个列表**：`routers/inquiries.py:247` 是
     `return [inquiry_to_schema(i, db) for i in rows]` —— 一行坏数据让
     `GET /api/inquiries` 对**所有用户**返回 500。实测：探针写入一次坏行后，
     列表端点持续 500，直到跑迁移才恢复。
     任何能调创建接口的客户端都握有"打挂主页面"的开关，且无法自愈。
- 顺带查清并**撤回**了我上一节登记的两条假缺陷（见"五度复评登记未做"首条的更正），
  以及一条同族的真缺陷：
  - `POST /api/inquiries` 的重试循环 `except IntegrityError: db.rollback()` 吞掉**一切**
    完整性冲突，然后统一报 500「编号生成冲突重试耗尽」。
    复现：把已存在的一条单改 `id` 后回 POST（其 `items[].id` 已存在）→
    连撞 5 次 → 500 且原因说错。这不是编号碰撞，重试多少次都会同样失败。
  - 另注：`inquiry_to_schema` 在 `db.commit()` **之后**才跑，所以"响应 500 但数据已落库"
    是可达状态（R32 的镜像：那次是失败说成功，这次是成功说失败）。
    本轮未改这个顺序，登记在下方"未做"。
- 修法（两处，成对交付）：
  1. **写边界改走读侧 schema**：`_build_inquiry_items` 先
     `InquiryItemSchema.model_validate(payload)`，通过后才构造 ORM 对象。
     这样"能写进去的"⊆"能读出来的"成为**构造性**保证，而不是逐列枚举类型；
     可无损转换的（`"10"` → 10）照样接受并按转换后的值落库，不可表示的在**任何写入之前**
     以 422 拒绝，detail 带 `error_type=invalid_inquiry_item`、`index`、`fields`。
     创建与更新两条路径共用此函数（`inquiries.py` 的两个调用点），一次修好两处。
  2. **迁移 0016 治已发生的坏行**（`alembic/versions/0016_repair_unrepresentable_item_fields.py`）：
     可转换就地改值；不可转换**删行 + 在父单 `inquiry_logs` 留一条 `DATA_REPAIR` 痕迹**，
     写明被删 item id 与原始值。刻意不选"置 0"（表上有 `CHECK (quantity > 0)`，0 会被拒），
     也不选"猜一个数"（那是替用户伪造业务事实）；`target_price` 不可转换则置 NULL
     （该列本就可空，NULL 是诚实的"不知道"）。`downgrade` 只收回留痕、不还原坏数据。
  3. 非编号冲突改判 409：`error_type=inquiry_conflict`，文案不再声称编号碰撞；
     真·重试耗尽保留 500 但改成结构化 detail（`inquiry_code_exhausted`）。
- 常驻用例（10 条，全部实跑）：
  - `backend/tests/test_inquiry_item_validation.py` 6 条。核心那条不是"这次请求返回 422"，
    而是**被拒之后 `GET /api/inquiries` 仍然 200 且行数不变** —— 只断状态抓不到"行已落库"。
  - `backend/tests/test_migration_0016_item_repair.py` 4 条：坏行被删+留痕、
    可转换值被改写不删除、**健康行一个都不动**（不开火的对照）、迁移幂等。
  - 控制档读数：把 `_build_inquiry_items` 退回改前 → 6 条全红；
    把 0016 迁移文件移走 → 4 条里 2 条开火（另 2 条本就是"不该变更"的守卫，
    有无迁移都应当绿，这是设计而非漏洞）。
  - 端到端复验（真实栈，非夹具）：`BEFORE GET /api/inquiries -> 500`
    → `alembic upgrade head`（`Running upgrade 0015 -> 0016`）
    → `AFTER GET /api/inquiries -> 200`，残留非整数行 0、`DATA_REPAIR` 留痕 2。
- 全量后端复算（CI 的 env 形状，`docker run --rm` 不导出 APP_ENV/DB_PATH 等）：
  `436 passed, 1 skipped, coverage 85.53% ≥ 80%`，对照修前基线 `426 passed` ——
  净增 10 条即本轮新用例，无回归。

  1. 三条用例共用固定 `items[].id="it-1"` → 第二条起撞主键 → 被那个吞掉一切的
     `except IntegrityError` 变成 500，读起来像"我的修复没生效"。
  2. 缺席断言写成 `"编号" not in message`，而修复后的文案里含"（非编号碰撞）"这种**否认**句
     → 假红。要钉的是被伪造的那句原因本身（`"编号生成冲突" not in message`），
     和 R33 那条"判别面必须只有修复才产出"是同一个道理。
- R35 的**全量 E2E 复跑读数**（改的是后端，前端与用例未变，但收尾要求"凭据必须晚于被采信的那棵树"）

### R39：一个组件测试文件**从未被类型检查过**（已修 + 常驻门禁）

- **现象**：`tsc --noEmit` 一直 rc=0，`vitest` 也照常跑它，但

- **成因**（外部测量报来、我亲手复现）：同目录下 `actionWorkbench.test.ts` 与
  `ActionWorkbench.test.tsx` 去掉扩展名后**大小写不敏感相等**；本 APFS 卷
  `useCaseSensitiveFileNames === false`，TS 的 `include` 展开会把后收集的那个丢掉。
  两个文件名各自都"正确地"对应自己的被测对象（`actionWorkbench.ts` / `ActionWorkbench.tsx`），
  所以这不是笔误，是**被测对象只差大小写**带来的结构性坑。
- **修法**：把纯逻辑那份改名为 `actionWorkbench.pure.test.ts`（`git mv`，保历史）而不给
  `tsconfig.json` 补 `files` —— 改名让这类撞名不再可能复发，`files` 只是给下一个受害者埋雷。
  复验：`tsc --noEmit` rc=0 且两个文件**都**进 listFiles（1/1）；
  `npx vitest run src/pages/dashboard/__tests__` → `3 files / 26 tests passed`（计数没因改名而少）。

  ⇒ 全仓开 `no-floating-promises` 会类型解析报错"。实测 `tsconfig.json:27` 是 `"include": ["src"]`
  且无 `exclude`，`tsc --listFilesOnly` 收 165 个 src 文件（含全部 `__tests__`）⇒ 那句是错的，
  真因就是上面这条撞名。**"因为 X 所以做不了"里的 X 也要实测。**

  差集非空判红；三条前提各判 rc=2 而不折算成通过（`git ls-files` 空 / `tsc` 非 0 / 分子为空）。
