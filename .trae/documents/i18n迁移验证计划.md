## 拟定变更

### 步骤 1：运行 TypeScript 类型检查

执行 `npx tsc --noEmit` 检查整个项目是否有类型错误。

### 步骤 2：分析结果并修复（仅在有错误时）

若 `npx tsc --noEmit` 报错，按错误类型修复：

**可能场景 A — `t()` 返回类型不兼容：**
- 极少见，`t()` 返回 `string`，兼容 `ReactNode`/`string` 类型 props
- 若出现，检查是否有 props 期望特定字面量类型

**可能场景 B — 缺少 `t` 依赖项（eslint 警告，非 tsc 错误）：**
- `useCallback` 中使用 `t` 但依赖数组未包含 `t` → 添加 `t` 到依赖数组
- 已确认 `validateStep`/`handleSaveDraft`/`handleSend` 已包含 `t` 在依赖中
- `buildInquiry` 当前不使用 `t`，若需迁移日志文案则需添加 `t` 到依赖

**可能场景 C — JSON key 不存在：**
- 无自定义类型增强，TypeScript 不会检测 key 是否存在
- 若运行时出现 key 缺失，`t()` 返回 key 本身（fallback 机制）

### 步骤 3：确认通过

若 `npx tsc --noEmit` 无错误输出，验证完成。

## 假设与决策

1. **迁移范围**：仅验证 5 个目标 React 文件的 i18n 迁移，不扩展到 `shared.ts`、`materialImport.ts` 等非目标文件
2. **数据 vs 文案**：日志内容字符串（`创建询价单 ${code}` 等）视为存储数据，按迁移规则排除
3. **验证标准**：`npx tsc --noEmit` 零错误即通过
4. **不修改业务逻辑**：仅修复类型错误（若有），不重构代码结构

## 验证步骤

1. 在项目根目录执行 `npx tsc --noEmit`
2. 检查输出：
   - 无输出（exit code 0）→ ✅ 验证通过
   - 有错误输出 → 记录错误，按步骤 2 修复，重新执行验证
3. 修复后再次执行 `npx tsc --noEmit` 确认零错误
